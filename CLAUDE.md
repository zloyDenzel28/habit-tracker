# Трекер полезных привычек

Пет-проект. Полные требования — в `docs/requirements.md`, он источник истины. Если задача противоречит этому документу, останови работу и спроси.

Автор проекта — системный аналитик, не разработчик. Объясняй решения кратко, но не пропускай места, где легко выстрелить себе в ногу.

## Стек

- **Бэкенд:** Python 3.12, FastAPI, SQLAlchemy (async) + Alembic, PostgreSQL 16
- **Планировщик:** APScheduler, отдельный процесс
- **Бот:** aiogram, режим polling
- **Фронт:** React + Vite + TypeScript
- **Всё запускается только через Docker Compose**

## Структура

```
backend/app/
  models/      # SQLAlchemy — общие для всех процессов
  services/    # бизнес-логика: переходы статусов, стрики
  fixtures/    # seed для отладки
  api/         # FastAPI-роутеры
  bot/         # aiogram: хендлеры кнопок
  scheduler/   # четыре джоба
  notifier.py  # Protocol + TelegramNotifier
  config.py    # pydantic-settings
backend/tests/ # юнит-тесты сервисного слоя, без БД
frontend/src/
docs/requirements.md
```

Три бэкенд-процесса (`api`, `worker`, `bot`) собираются из одного образа и делят `models/` и `services/`. Различаются только командой запуска.

## Ключевые инварианты

Нарушение любого из них — баг, даже если тесты проходят.

1. **Habit — это шаблон, Occurrence — конкретное выполнение в конкретный день.** Вся история, статусы и статистика живут на occurrence. Никогда не хранить состояние выполнения в Habit.
2. **Всё время внутри системы — UTC.** `TZ=UTC` во всех контейнерах. Локальное время получается только через `User.timezone` (IANA) в момент отображения или расчёта `local_date`. Никогда не полагаться на таймзону хоста.
3. **`Habit.schedule_time` хранится как локальное время без TZ**, не как UTC. Иначе переход на летнее время сдвинет расписание.
4. **Бизнес-логика живёт в `services/`**, не в роутерах и не в хендлерах бота. API и бот — тонкие адаптеры: разобрали ввод, вызвали сервис, отдали ответ. Одно действие («выполнил») должно работать одинаково из веба и из Telegram.
5. **Отправка уведомлений — только через `Notifier`.** Никаких прямых вызовов aiogram из сервисов или планировщика.
6. **Планировщик опрашивает БД, а не держит таймеры в памяти.** Таймеры не переживают рестарт контейнера.
7. **Джобы идемпотентны.** Повторный запуск не должен создавать дубли occurrences или слать уведомление второй раз. Защита: уникальный индекс `(habit_id, scheduled_at)` и поля `notified_at` / `followup_sent_at`.
8. **`HabitPause` создаётся только по явному действию пользователя.** Системных пауз нет.

## Версии библиотек

Пиши код строго под эти версии. Это те места, где легче всего смешать несовместимые поколения API.

| Библиотека | Версия | На что обратить внимание |
|---|---|---|
| aiogram | 3.x | Роутеры и декораторы v3. Синтаксис v2 несовместим |
| SQLAlchemy | 2.0.x, async | Стиль 2.0 (`select()`), `AsyncSession`. Не legacy Query API |
| Pydantic | v2 + pydantic-settings v2 | Не смешивать с валидаторами v1 |
| APScheduler | 3.x | API 4.x несовместим |
| FastAPI | последняя стабильная | Lifespan вместо `@app.on_event` |
| Alembic | последняя стабильная | Async-совместимый `env.py` |

Если сомневаешься в актуальном API любой из них — подтяни документацию через Context7 (`use context7`), а не пиши по памяти. Особенно это касается aiogram, SQLAlchemy и APScheduler.

Не вызывай Context7 на задачах, где он не нужен: правки вёрстки, рефакторинг, работа с Docker Compose. Каждый вызов расходует контекст.

## Команды

```bash
docker compose up --build          # поднять всё
docker compose logs -f worker      # смотреть планировщик
docker compose exec api alembic revision --autogenerate -m "..."
docker compose exec api alembic upgrade head
docker compose exec db psql -U postgres -d habits
docker compose exec api python -m app.fixtures.seed
docker compose exec api pytest     # юнит-тесты сервисного слоя
docker compose down -v             # снести вместе с данными БД
```

## Договорённости по коду

- Async везде на бэке: `asyncpg`, async-сессии SQLAlchemy.
- Конфиг только через `pydantic-settings` и переменные окружения. Никаких хардкодов хоста БД, токенов и интервалов.
- `SCHEDULER_TICK_SECONDS` берётся из конфига — на отладке ставится в 5 секунд.
- Комментарии на русском там, где логика неочевидна (расчёт стриков, обработка таймзон, условия догоняющего пинга).
- Имена статусов из документа менять нельзя: `pending`, `notified`, `snoozed`, `in_progress`, `done`, `skipped`, `missed`, `paused`.

## Порядок работы

Проект строится по шагам, каждый — отдельная сессия:

1. Каркас: compose, Dockerfile'ы, конфиг, модели, первая миграция ✅ критерий: `docker compose up` работает, таблицы созданы
2. Сервисный слой: переходы статусов, расчёт стриков, фикстуры ✅ критерий: `pytest` зелёный, `seed` считает серии верно
3. Планировщик: три джоба, отправка замокана логами
4. Бот: хендлеры кнопок, реальная отправка
5. Фронт: экраны из раздела 9 ✅
6. Синхронизация чата: `sent_messages`, четвёртый джоб — действие в вебе гасит сообщение в Telegram ✅ критерий: оба сообщения гаснут за один тик

Не забегай вперёд. Если просят шаг 2, не начинай писать бота.

### Коммиты

Коммить по ходу шага, не одной кучей в конце. Как только законченный кусок проверен — отдельный коммит: миграция, слой, тесты, фикстуры, документация идут разными. Спрашивать разрешения на каждый коммит не надо, это договорённость.

Прямо в `main`, веток не заводим — проект одного человека, ревью и CI нет.

Сообщения на русском, в повелительном или изъявительном наклонении, как в существующей истории: «Alembic и первая миграция», «Фиксирую версии фронта lock-файлом». Не `feat:`/`fix:`, не английский.

Не коммитить: `.env`, содержимое `pgdata`, временные скрипты проверки.

Пуш — один раз в конце шага, когда критерий выполнен и `HANDOFF.md` обновлён. Не после каждого коммита: пока коммиты локальны, их можно переписать, а отправленную историю из GitHub так просто не убрать. Перед пушем проверить, что в диффе нет токенов и telegram_id.

## Чего не делать

- Не добавлять фичи из раздела «Не входит в MVP» (web push, ачивки, ретроспективная отметка, несколько времён на привычку).
- Не выносить фронт и бэк в разные репозитории.
- Не заменять polling на webhook — локально это потребует туннеля.
- Не поднимать планировщик внутри процесса API.
- Не использовать `datetime.now()` без таймзоны. Только `datetime.now(timezone.utc)`.
