# Параллельные субагенты — план на волну README + ERD

Черновой прогон параллельной работы через субагентов Claude Code, ради опыта.
`HANDOFF.md` и `PROMPTS.md` остаются главными документами о состоянии проекта;
этот файл — только про механику одной параллельной волны и разовый, его можно
удалить после того, как волна пройдена.

## Что такое параллельные субагенты здесь

В Claude Code есть инструмент Agent (Task): им можно за один ответ запустить
несколько подпроцессов одновременно. С флагом `isolation: "worktree"` каждый
получает свою временную git worktree и свою временную ветку — правит файлы
в изолированной копии репозитория, не задевая рабочую директорию и не мешая
второму агенту. Оба бегут параллельно в фоне; сессия получает уведомление
по мере готовности каждого.

Это не то же самое, что делали до сих пор в `PROMPTS.md` — там сессии шли
одна за другой через `/clear` в одном окне. Здесь несколько агентов работают
одновременно, каждый в своей ветке, а в конце их результат сводится в `main`
вручную.

## Когда это имеет смысл, а когда нет

**Подходит:** независимые задачи над разными файлами без общей развилки.
README.md и docs/erd.md — ровно такой случай: разные файлы, разные источники
(README смотрит на docker-compose.yml и требования, ERD — строго на код
моделей), результат одного не влияет на результат другого.

**Не подходит:**
- Сессия 7 (C4 + сиквенсы, см. `PROMPTS.md`) — её собственный промпт прямо
  требует прочитать готовые README и ERD и не дублировать их, то есть она
  зависит от результата этой волны и не может стартовать параллельно с ней.
- Внутри самой сессии 7 дробить C4 и сиквенсы на двух агентов тоже не стоит:
  там единое судейское решение о том, что́ **не** рисовать, и если его делят
  два агента, решения разъедутся стилистически и по границам.
- Шаг 6 (синхронизация чата, находка 2) — это код, трогающий общие модели
  и три процесса разом. Параллелить нечего, оставляем отдельной сессией,
  как и было.

## Итоговый план

1. **Волна 1 (параллельно, 2 субагента, worktree-изоляция):** README.md
   и docs/erd.md — промпты ниже.
2. **Слияние в main:** проверить diff каждой ветки глазами, cherry-pick
   по одному коммиту, удалить временные ветки и worktree.
3. **Дальше — как в PROMPTS.md, без изменений:** сессия 7 (C4+сиквенсы,
   Opus), затем шаг 6 (синхронизация чата, Opus). Обе последовательные,
   не параллельные.

## Шаг за шагом

### 0. Предусловия

`git status` чист (сейчас так и есть). Отдельно открывать терминалы или
новые окна Claude Code не нужно — субагенты живут внутри текущей сессии,
а не в отдельных процессах, которые нужно поднимать руками.

### 1. Запустить двух субагентов одним сообщением

В этом же окне Claude Code, без `/clear` (субагентам история чата не нужна —
у каждого свой самодостаточный промпт), попросить:

> Спавни двух субагентов параллельно, у каждого своя git worktree-изоляция
> (`isolation: "worktree"`, `subagent_type: "general-purpose"`, `model: "sonnet"`):
> — Агент 1 пишет README.md, промпт для него в PARALLEL-AGENTS.md
> — Агент 2 пишет docs/erd.md, промпт для него в PARALLEL-AGENTS.md
> Запусти оба в одном ответе, чтобы они реально пошли параллельно.

Под капотом это два вызова инструмента Agent в одном ответе ассистента —
именно одновременность вызовов в одном сообщении даёт параллельность,
не последовательность.

### 2. Дождаться завершения

Оба агента фоновые — уведомления придут по мере готовности каждого,
пинать и переспрашивать не нужно.

### 3. Проверить и свести в main

Для каждой готовой ветки — сначала посмотреть, что агент реально сделал,
и только потом переносить:

```
git -C c:/Projects/habit-tracker log <branch1> -1 --stat
git -C c:/Projects/habit-tracker show <branch1>

git -C c:/Projects/habit-tracker cherry-pick <commit1>
git -C c:/Projects/habit-tracker worktree remove <path1>
git -C c:/Projects/habit-tracker branch -d <branch1>

# то же самое для второй ветки
```

Cherry-pick, а не `git merge`, — намеренно: `CLAUDE.md` держит правило
«прямо в main, веток не заводим», временные worktree-ветки существуют
только на время работы агента и должны исчезнуть после переноса, не
оставляя merge-коммитов в истории.

### 4. Дальше — последовательно

Сессия 7 из `PROMPTS.md` (C4 + сиквенсы) без изменений в промпте — теперь
она реально может свериться с готовыми README и ERD, как и просит её текст.

## Опасные места, специфика этого проекта

- Если оба агента внезапно тронут один и тот же файл (например, один решит
  заодно поправить `HANDOFF.md`) — второй cherry-pick упадёт в конфликт.
  Промпты ниже явно ограничивают каждого агента его файлом, но `git show`
  перед переносом всё равно стоит прочитать, а не доверять вслепую.
- `.env` и `pgdata` не коммитятся — правило общее для всех worktree одного
  репозитория, но после cherry-pick не лишне проверить `git status`.
- Context7 на этих двух задачах не нужен — правки маркдауна, не библиотечный
  код; вызывать его агентам незачем, это будет просто тратой контекста
  (см. `CLAUDE.md`, раздел про версии библиотек).
- Оба агента получают `model: "sonnet"` явно — `PROMPTS.md` для сессии 6
  (README+ERD, механический перенос) рекомендует именно Sonnet, Opus здесь
  жечь не на что.

## Промпты для волны 1

### Агент 1 — README.md

```
Ты работаешь в репозитории пет-проекта «Трекер полезных привычек»
(Python 3.12/FastAPI бэкенд, React+Vite+TS фронт, всё поднимается только
через Docker Compose). Прочитай CLAUDE.md в корне (архитектурные инварианты
и структура репозитория), HANDOFF.md (текущий статус: план MVP пройден
целиком, все находки ручного тестирования закрыты) и docker-compose.yml
плюс .env.example в корне (список сервисов и переменных окружения).

Задача: написать README.md в корне репозитория — для человека, который
видит проект впервые. Должно быть: что это за приложение, как его поднять
(`docker compose up --build`, что нужно заранее подготовить в .env — смотри
.env.example), из каких процессов оно состоит (api/worker/bot/web/db —
роли каждого, бери из CLAUDE.md и docker-compose.yml), куда смотреть при
отладке (какие логи смотреть, команды есть в CLAUDE.md, раздел «Команды»).

Не пересказывай содержимое HANDOFF.md (история решений и находок — документ
для автора-через-месяц) и CLAUDE.md (правила для ИИ-агента) — если нужно
на них сослаться, дай ссылку одной строкой, не копируй содержимое.

Не трогай docs/erd.md, docs/requirements.md и любые другие файлы — этим
параллельно занимается другой агент. Правь только README.md.

Закоммить одним коммитом. Сообщение — на русском, в повелительном или
изъявительном наклонении, как в `git log` этого репозитория (посмотри
последние коммиты командой `git log --oneline -10` для стиля), без
префиксов вида feat:/fix:.
```

### Агент 2 — docs/erd.md

```
Ты работаешь в репозитории пет-проекта «Трекер полезных привычек»
(Python 3.12/FastAPI/SQLAlchemy async бэкенд). Прочитай CLAUDE.md в корне —
там описаны ключевые инварианты, особенно первый: Habit — это шаблон
привычки, Occurrence — конкретное выполнение в конкретный день, и вся
история/статусы/статистика живут на Occurrence, а не на Habit.

Задача: собрать ER-диаграмму на Mermaid (`erDiagram`) в docs/erd.md.
Источник истины — строго код в backend/app/models/ (прочитай все файлы
там), а не docs/requirements.md и не общие знания о таком приложении:
поля, типы, nullable, внешние ключи и уникальные индексы бери из
SQLAlchemy-моделей построчно — автор будет сверять диаграмму с кодом
построчно.

Диаграмма должна визуально показывать ключевой инвариант без чтения
текста рядом: Occurrence несёт на себе статус и все временные метки
выполнения (started_at, finished_at, notified_at и подобные), Habit —
только шаблон расписания. Подпиши связи между таблицами.

Формат — mermaid-блок прямо внутри markdown-файла (GitHub рендерит без
плагинов), никаких внешних картинок и инструментов.

Не трогай README.md и другие файлы — этим параллельно занимается другой
агент. Правь только docs/erd.md.

Закоммить одним коммитом. Сообщение — на русском, в повелительном или
изъявительном наклонении, как в `git log` этого репозитория (посмотри
последние коммиты командой `git log --oneline -10` для стиля), без
префиксов вида feat:/fix:.
```

## На будущее

Других независимых пар в оставшемся бэклоге (`PROMPTS.md`, раздел
«Порядок») сейчас нет — сессия 7 зависит от этой волны, шаг 6 меняет общий
код. Если бэклог пополнится независимыми документами (например, отдельно
гайд по деплою и отдельно гайд по локальной отладке бота) — тот же рецепт
подойдёт снова: два самодостаточных промпта, `isolation: "worktree"`,
cherry-pick вместо merge.
