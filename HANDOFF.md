### Состав сервисного слоя

| Модуль | Что внутри |
|---|---|
| `timeutils` | единственное место перехода UTC ↔ локальное время |
| `constants` | числа из спеки: 5 минут, 5 снузов, 14 дней паузы, 30 дней окна |
| `errors` | доменные исключения, которые ловят адаптеры |
| `occurrences` | переходы статусов (§4) и выборки диспетчера (§6.2, §6.3) |
| `generation` | создание occurrences по расписанию (§6.1) |
| `pauses` | отрезки пауз с учётом досрочного снятия |
| `habits` | создание, правка, архив, пауза, смена таймзоны, пересечения (§8, §9) |
| `stats` | стрики и статистика (§7) |
| `messages` | тексты уведомлений, наборы кнопок и разбор `callback_data` (§5) |
| `users` | поиск пользователя по `telegram_id` |

Переходы статусов синхронные и не трогают сессию: они меняют загруженный объект, а `commit` делает вызывающий адаптер. Поэтому одно действие пользователя остаётся одной транзакцией, а правила проверяются юнит-тестами без Postgres.

| Кнопка | Что зовёт |
|---|---|
| ▶️ Начал | `occurrences.start` |
| ⏰ +5 мин | `occurrences.snooze` |

| 🚫 Пропустить сегодня / ❌ Не получилось | `occurrences.skip` |

Оговорки, которые всплыли на шагах 1-4:
- Версии фронта зафиксированы `package-lock.json`, образ ставит их через `npm ci`. Без lock-файла установка занимала ~25 минут вместо 7 секунд
- `paused` считается нетерминальным статусом: §4 называет его терминальным, но там же описан переход `paused → pending`
- `pytest` ставится в тот же образ через `.[dev]`. Проект локальный, отдельная сборка под тесты сложнее, чем польза от неё
- В образе стоит APScheduler 3.11. Это важно: 3.10 принимал только таймзоны pytz, а 3.11 перешёл на `zoneinfo`. В коде таймзона везде передаётся строкой `"UTC"` — её разбирают обе версии
- Логи `apscheduler.executors` приглушены до WARNING: на отладочном тике в 5 секунд две строки INFO на каждый запуск джоба забивают вывод
- В образе стоит aiogram 3.30. Синтаксис v2 несовместим полностью, а v4 уже вышел и тоже ломающий — проверяй, что подсказка не из другого поколения
- `TELEGRAM_BOT_TOKEN` пуст — всё поднимается: воркер уходит на `LogNotifier` и пишет об этом, бот логирует предупреждение и просто ждёт

## Ключевые решения и почему они такие

Эти решения обсуждались и приняты осознанно. Не предлагай их изменить без веской причины.

| Решение | Обоснование |
|---|---|
| Уведомления через Telegram, не web push | В Safari/iOS нет кнопок в уведомлениях, а кнопки — суть продукта |
| Веб-интерфейс на React + Telegram как транспорт | Веб для CRUD и статистики, TG для уведомлений с кнопками |
| Habit и Occurrence — разные сущности | Без второй невозможны статусы, история и стрики |
| Occurrences генерируются заранее ночным джобом | Проще планировщик и отладка, видно что запланировано |
| Планировщик опрашивает БД, а не держит таймеры | Таймеры не переживают рестарт контейнера |
| Polling у бота, не webhook | Локально webhook требует туннеля |
| Длительность по умолчанию 5 минут, минимум 5 | Убирает класс «привычек без длительности» |
| Таймер выполнения от нажатия «Начал» | Человек может начать не ровно в плановое время |
| Снуз максимум 5 раз по 5 минут | Дальше — `missed` |
| `skipped` и `missed` ломают стрик одинаково | Решение автора: осознанный отказ не лучше игнора |
| Пауза не ломает стрик, но >14 дней обнуляет | Компромисс между мягкостью и эксплойтом «ставлю паузу когда лень» |
| Восстановление из архива обнуляет стрик | Иначе архив = бесконечная пауза в обход правила 14 дней |
| Монорепозиторий, не отдельные репо | Compose описывает оба; изменения контракта должны быть атомарными |
| Всё в Docker Compose, локально | Цель проекта — научиться, а не выкатить в прод |
| Ретроспективная отметка вне MVP | Обесценивает статистику |
| `notified → done` и `in_progress → skipped` разрешены (шаг 2) | §4 их не описывает, но §5 даёт эти кнопки на догоняющем пинге. Без них кнопка «Выполнил» тому, кто не отреагировал, не работала бы |
| «Не получилось» → `skipped`, не `missed` (шаг 2) | Человек ответил осознанно. `missed` по §11 означает «не отреагировал вовсе» и потому неизменяем |
| Колонка `Habit.streak_reset_on` (шаг 2, миграция `0002`) | §8 требует обнулить серию при восстановлении из архива, но прошлые `done` остаются в occurrences. Без отметки серия продолжилась бы. Рекорд считается по всей истории и отметку игнорирует |
| Снуз отсчитывает 5 минут от нажатия, а не от старого `current_due_at` (шаг 2) | По букве §4 это `+= 5`, но если отреагировать через 20 минут, новое время окажется в прошлом и напоминание придёт мгновенно. Кнопка обещает «через пять минут» |
| Догоняющий пинг для `notified` считается от `GREATEST(current_due_at, notified_at)` (шаг 3) | По букве §6.2 это `current_due_at + duration`. Но если occurrence просрочен дольше своей длительности (воркер стоял, сид сделан давно), оба условия §6.2 истинны в одном тике и человек получает «пора» и «успел?» подряд. В штатном режиме `notified_at ≈ current_due_at` и поведение то же. По смыслу это та же поправка, что и в снузе |
| Закрытие дня не проверяет «наступила ли полночь» (шаг 3) | Для каждого пользователя берётся его текущая локальная дата и закрывается всё, что раньше неё. Результат тот же, но не надо помнить, когда джоб отработал в прошлый раз: повторный запуск в том же часу находит 0 записей (инвариант 7). Заодно суточный простой контейнера закроет все пропущенные дни, а не только последний |
| Диспетчер сначала отправляет, потом ставит отметку (шаг 3) | Обратный порядок при сбое отправки означал бы, что человек уведомления не увидел, а occurrence уже `notified`. Падение между отправкой и коммитом даёт повтор на следующем тике — это заметно менее неприятно. Всё внутри одной транзакции, строки держит `FOR UPDATE ... SKIP LOCKED` |
| Разовый прогон генератора при старте воркера (шаг 3) | Расписание APScheduler живёт в памяти, поэтому пропущенное за простой контейнера 03:00 сам он не отработает. Джоб идемпотентен, лишний запуск ничего не портит |
| Тексты уведомлений размечены HTML, название экранируется (шаг 3) | Легаси-Markdown у Telegram спотыкается на подчёркиваниях и звёздочках в пользовательском тексте, в HTML достаточно экранировать три символа. Название привычки вводит пользователь |
| Набор кнопок первого уведомления не спрашивает `occurrences.can_snooze` (шаг 3) | `can_snooze` требует статуса `notified`, а диспетчер сначала отправляет и только потом помечает — на момент сборки текста запись ещё `pending`, и кнопка «+5 мин» не показывалась никогда. `reminder()` вызывается ровно для уходящего уведомления, поэтому проверяет только остаток снузов. Нашлось на живом прогоне: юнит-тест закреплял ошибочное поведение |
| Ошибка отправки не роняет весь тик (шаг 3) | Одна недоставленная запись не должна мешать остальной пачке. Отметка при этом не ставится — попробуем на следующем тике |
| `TelegramNotifier` отдельным модулем `app/telegram.py` (шаг 4) | В `notifier.py` остались протокол и `LogNotifier`, и он ничего не знает про aiogram. Этот модуль тянет `services/messages.py`, а через него — юнит-тесты; подтягивать за собой пол-фреймворка им незачем |
| `parse_mode=HTML` задан один раз в `create_bot` через `DefaultBotProperties` (шаг 4) | Тексты уже размечены HTML. Указывать разметку в каждом вызове означало бы однажды забыть и показать человеку сырые теги |
| Разбор `callback_data` лежит в `services/messages.py` рядом со сборкой (шаг 4) | Формат один. Если собирать строку в сервисах, а разбирать в боте, они однажды разойдутся — и молча, потому что кнопка просто перестанет отвечать |
| `parse_callback_data` возвращает `None`, а не поднимает исключение (шаг 4) | Строка приходит снаружи и может быть какой угодно: от кнопки старой версии бота до подделки. Это штатный ввод, а не сбой |
| После нажатия бот дописывает итог в сообщение и убирает кнопки (шаг 4) | Кнопка под старым сообщением живёт вечно. Без отметки через день не понять, отвечал ты на это уведомление или нет. Текст итога (`messages.action_note`) в сервисах, чтобы веб на шаге 5 говорил то же самое |
| Доменные ошибки — реплика через `callback.answer`, а не падение (шаг 4) | `AlreadyInStatus`, `InvalidTransition` и `SnoozeLimitReached` на кнопках — норма, а не баг: двойное нажатие и нажатие на уже закрытом занятии случаются постоянно |
| `/start` не заводит пользователей (шаг 4) | Их создаёт сид (§12.5), а `telegram_id` уникален — заведённый ботом пользователь подрался бы с сид-пользователем. `/start` показывает id, чтобы его было откуда взять для `.env` |
| `allowed_updates` ограничен `message` и `callback_query` (шаг 4) | Остальные типы апдейтов Telegram копит, пока контейнер стоит, и отдаёт пачкой при старте |
| Есть хендлер-заглушка на любой незнакомый `callback_data` (шаг 4) | Без ответа Telegram крутит часики на кнопке около минуты — выглядит как зависший бот |
| Сообщение старше 48 часов не редактируется, действие всё равно записано (шаг 4) | Telegram отдаёт такое как `InaccessibleMessage`. Отказываться из-за этого от перехода статуса было бы хуже: человек нажал осознанно |

## Что пригодится на шаге 5

- **Бэкенд для фронта ещё не написан.** `app/api/main.py` — это `/health` и больше ничего. Роутеры (§9) и `POST /auth/dev-login` (§12.4) делаются на шаге 5, сервисный слой под них уже готов целиком.
- **API — такой же тонкий адаптер, как бот и джобы (инвариант 4).** Одно действие обязано вести себя одинаково из веба и из Telegram, поэтому «Выполнил» на экране «Сегодня» зовёт ту же `occurrences.complete`, что и кнопка в чате. Смотри `app/bot/handlers.py` как на образец: разобрал ввод, позвал сервис, поймал доменную ошибку, отдал ответ. В роутере доменные исключения превращаются не в реплику, а в HTTP-код.
- **Готовые выборки под экраны:** `occurrences.list_for_local_date` — «Сегодня», `habits.habits_of_user` — «Привычки», `stats.habit_stats` и `stats.heatmap` — «Статистика».
- **Локальная дата берётся из `habits.user_today`, а не из браузера.** Инвариант 2: единственный источник локального времени — `User.timezone`.
- **Вход:** при `DEV_AUTH=true` — `POST /auth/dev-login` на сид-пользователя, фронт показывает «Войти как тестовый пользователь» вместо виджета. Пользователя ищет `users.get_by_telegram_id`.
- **Фронт пока пустой.** `frontend/src/App.tsx` — заглушка Vite. Версии зафиксированы `package-lock.json`, ставить новые пакеты — только с обновлением lock-файла, иначе сборка образа растянется на полчаса.

## Как отлаживать бота

- **Поставь `SCHEDULER_TICK_SECONDS=5` в `.env`.** По умолчанию 60. После отладки верни обратно, иначе тик в пять секунд будет молотить всё время.
- **Сид ставит «Отжимания» на три минуты вперёд:** `docker compose exec api python -m app.fixtures.seed`, дальше `docker compose logs -f worker bot`.
- **Сид пересоздаёт пользователя.** Каскад по FK уносит вместе с ним все привычки и историю, так что нажатия, сделанные до сида, в БД не останутся.
- **Чтобы уведомления ушли в лог, а не в чат** — очисти `TELEGRAM_BOT_TOKEN`: воркер сам переключится на `LogNotifier`.
- **Смотреть состояние:** `docker compose exec db psql -U postgres -d habits -c "select h.title, o.status, o.snooze_count from occurrences o join habits h on h.id=o.habit_id where o.local_date = current_date;"`
