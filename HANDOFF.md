# HANDOFF: перенос проекта в Cowork

## Что это за проект

Трекер полезных привычек. Пет-проект одного человека, цель — научиться собирать приложение с нуля через вайб-кодинг. Автор — системный аналитик, не разработчик.

## Где мы сейчас

**Стадия:** план MVP пройден целиком — шаги 1-5b сделаны, все пятнадцать находок ручного тестирования разобраны (см. «Статус находок»).

Готово:
- `docs/requirements.md` — полная спека MVP v1.3, актуализирована по итогам находок
- `CLAUDE.md` — правила работы с кодовой базой и инварианты
- **Шаг 1:** compose на шесть сервисов, образы бэка и фронта, конфиг, четыре модели, миграция `0001`, три точки входа
- **Шаг 2:** `app/services/` — восемь модулей, миграция `0002`, фикстуры
- **Шаг 3:** `app/scheduler/` — три джоба и расписание APScheduler, `services/messages.py`, `LogNotifier`
- **Шаг 4:** `app/telegram.py` — `TelegramNotifier`, `app/bot/handlers.py` — хендлеры кнопок и `/start`, `services/users.py`
- **Шаг 5a:** `app/api/` — дев-логин, роутеры привычек/occurrences/пользователя, схемы, единый обработчик доменных ошибок
- **Шаг 5b:** `frontend/src/` — пять экранов раздела 9, клиент API, мини-роутер на хэше, прокси Vite вместо CORS

Каждый шаг проверен и руками на живом стенде (curl/Playwright/psql/Telegram), и автотестами; подробности конкретных прогонов не дублируются здесь — они в истории git и в коммитах соответствующих сессий. Текущее состояние: `pytest` — 110 тестов, зелёный; `tsc` и `npm run build` без ошибок.

Находка 2 (действие в вебе не отражается в сообщении Telegram) не закрыта — ждёт шага 6, см. раздел «Что дальше». Остальные четырнадцать закрыты, что именно сделано — в разделе «Статус находок».

### Состав сервисного слоя

| Модуль | Что внутри |
|---|---|
| `timeutils` | единственное место перехода UTC ↔ локальное время |
| `constants` | числа из спеки: 5 минут, 5 снузов, 14 дней паузы, 30 дней окна |
| `errors` | доменные исключения, которые ловят адаптеры |
| `occurrences` | переходы статусов (§4) и выборки диспетчера (§6.2, §6.3) |
| `generation` | создание occurrences по расписанию (§6.1) |
| `pauses` | отрезки пауз с учётом досрочного снятия |
| `habits` | создание, правка, архив, пауза, смена таймзоны, пересечения (§8, §9) |
| `stats` | стрики и статистика (§7) |
| `messages` | тексты уведомлений, наборы кнопок и разбор `callback_data` (§5) |
| `users` | поиск пользователя по `telegram_id` |

Переходы статусов синхронные и не трогают сессию: они меняют загруженный объект, а `commit` делает вызывающий адаптер. Поэтому одно действие пользователя остаётся одной транзакцией, а правила проверяются юнит-тестами без Postgres.

Оговорки, которые всплыли на шагах 1-4:
- Версии фронта зафиксированы `package-lock.json`, образ ставит их через `npm ci`. Без lock-файла установка занимала ~25 минут вместо 7 секунд
- `paused` считается нетерминальным статусом: §4 называет его терминальным, но там же описан переход `paused → pending`
- `pytest` ставится в тот же образ через `.[dev]`. Проект локальный, отдельная сборка под тесты сложнее, чем польза от неё
- В образе стоит APScheduler 3.11. Это важно: 3.10 принимал только таймзоны pytz, а 3.11 перешёл на `zoneinfo`. В коде таймзона везде передаётся строкой `"UTC"` — её разбирают обе версии
- Логи `apscheduler.executors` приглушены до WARNING: на отладочном тике в 5 секунд две строки INFO на каждый запуск джоба забивают вывод
- В образе стоит aiogram 3.30. Синтаксис v2 несовместим полностью, а v4 уже вышел и тоже ломающий — проверяй, что подсказка не из другого поколения
- `TELEGRAM_BOT_TOKEN` пуст — всё поднимается: воркер уходит на `LogNotifier` и пишет об этом, бот логирует предупреждение и просто ждёт
- **Правку `.env` подхватывает `docker compose up -d <сервис>`, а не `restart`.** `restart` поднимает контейнер с тем окружением, с которым тот был создан, и молча работает по-старому. Правку кода, наоборот, хватает и `restart`: исходники смонтированы томом. Ловится по строчке «тик диспетчера = N c» в логе воркера

## Ключевые решения и почему они такие

Эти решения обсуждались и приняты осознанно. Не предлагай их изменить без веской причины.

| Решение | Обоснование |
|---|---|
| Уведомления через Telegram, не web push | В Safari/iOS нет кнопок в уведомлениях, а кнопки — суть продукта |
| Веб-интерфейс на React + Telegram как транспорт | Веб для CRUD и статистики, TG для уведомлений с кнопками |
| Habit и Occurrence — разные сущности | Без второй невозможны статусы, история и стрики |
| Occurrences генерируются заранее ночным джобом | Проще планировщик и отладка, видно что запланировано |
| Планировщик опрашивает БД, а не держит таймеры | Таймеры не переживают рестарт контейнера |
| Polling у бота, не webhook | Локально webhook требует туннеля |
| Длительность по умолчанию 5 минут, минимум 5 | Убирает класс «привычек без длительности» |
| Таймер выполнения от нажатия «Начал» | Человек может начать не ровно в плановое время |
| Снуз максимум 5 раз по 5 минут | Дальше — `missed` |
| `skipped` и `missed` ломают стрик одинаково | Решение автора: осознанный отказ не лучше игнора |
| Пауза не ломает стрик, но >14 дней обнуляет | Компромисс между мягкостью и эксплойтом «ставлю паузу когда лень» |
| Восстановление из архива обнуляет стрик | Иначе архив = бесконечная пауза в обход правила 14 дней |
| Монорепозиторий, не отдельные репо | Compose описывает оба; изменения контракта должны быть атомарными |
| Всё в Docker Compose, локально | Цель проекта — научиться, а не выкатить в прод |
| Ретроспективная отметка вне MVP | Обесценивает статистику |
| `notified → done` и `in_progress → skipped` разрешены (шаг 2) | §4 их не описывает, но §5 даёт эти кнопки на догоняющем пинге. Без них кнопка «Выполнил» тому, кто не отреагировал, не работала бы |
| «Не получилось» → `skipped`, не `missed` (шаг 2) | Человек ответил осознанно. `missed` по §11 означает «не отреагировал вовсе» и потому неизменяем |
| Колонка `Habit.streak_reset_on` (шаг 2, миграция `0002`) | §8 требует обнулить серию при восстановлении из архива, но прошлые `done` остаются в occurrences. Без отметки серия продолжилась бы. Рекорд считается по всей истории и отметку игнорирует |
| Снуз отсчитывает 5 минут от нажатия, а не от старого `current_due_at` (шаг 2) | По букве §4 это `+= 5`, но если отреагировать через 20 минут, новое время окажется в прошлом и напоминание придёт мгновенно. Кнопка обещает «через пять минут» |
| Догоняющий пинг для `notified` считается от `GREATEST(current_due_at, notified_at)` (шаг 3) | По букве §6.2 это `current_due_at + duration`. Но если occurrence просрочен дольше своей длительности (воркер стоял, сид сделан давно), оба условия §6.2 истинны в одном тике и человек получает «пора» и «успел?» подряд. В штатном режиме `notified_at ≈ current_due_at` и поведение то же. По смыслу это та же поправка, что и в снузе |
| Закрытие дня не проверяет «наступила ли полночь» (шаг 3) | Для каждого пользователя берётся его текущая локальная дата и закрывается всё, что раньше неё. Результат тот же, но не надо помнить, когда джоб отработал в прошлый раз: повторный запуск в том же часу находит 0 записей (инвариант 7). Заодно суточный простой контейнера закроет все пропущенные дни, а не только последний |
| Диспетчер сначала отправляет, потом ставит отметку (шаг 3) | Обратный порядок при сбое отправки означал бы, что человек уведомления не увидел, а occurrence уже `notified`. Падение между отправкой и коммитом даёт повтор на следующем тике — это заметно менее неприятно. Всё внутри одной транзакции, строки держит `FOR UPDATE ... SKIP LOCKED` |
| Разовый прогон генератора при старте воркера (шаг 3) | Расписание APScheduler живёт в памяти, поэтому пропущенное за простой контейнера 03:00 сам он не отработает. Джоб идемпотентен, лишний запуск ничего не портит |
| Тексты уведомлений размечены HTML, название экранируется (шаг 3) | Легаси-Markdown у Telegram спотыкается на подчёркиваниях и звёздочках в пользовательском тексте, в HTML достаточно экранировать три символа. Название привычки вводит пользователь |
| Набор кнопок первого уведомления не спрашивает `occurrences.can_snooze` (шаг 3) | `can_snooze` требует статуса `notified`, а диспетчер сначала отправляет и только потом помечает — на момент сборки текста запись ещё `pending`, и кнопка «+5 мин» не показывалась никогда. `reminder()` вызывается ровно для уходящего уведомления, поэтому проверяет только остаток снузов. Нашлось на живом прогоне: юнит-тест закреплял ошибочное поведение |
| Ошибка отправки не роняет весь тик (шаг 3) | Одна недоставленная запись не должна мешать остальной пачке. Отметка при этом не ставится — попробуем на следующем тике |
| `TelegramNotifier` отдельным модулем `app/telegram.py` (шаг 4) | В `notifier.py` остались протокол и `LogNotifier`, и он ничего не знает про aiogram. Этот модуль тянет `services/messages.py`, а через него — юнит-тесты; подтягивать за собой пол-фреймворка им незачем |
| `parse_mode=HTML` задан один раз в `create_bot` через `DefaultBotProperties` (шаг 4) | Тексты уже размечены HTML. Указывать разметку в каждом вызове означало бы однажды забыть и показать человеку сырые теги |
| Разбор `callback_data` лежит в `services/messages.py` рядом со сборкой (шаг 4) | Формат один. Если собирать строку в сервисах, а разбирать в боте, они однажды разойдутся — и молча, потому что кнопка просто перестанет отвечать |
| `parse_callback_data` возвращает `None`, а не поднимает исключение (шаг 4) | Строка приходит снаружи и может быть какой угодно: от кнопки старой версии бота до подделки. Это штатный ввод, а не сбой |
| После нажатия бот дописывает итог в сообщение и убирает кнопки (шаг 4) | Кнопка под старым сообщением живёт вечно. Без отметки через день не понять, отвечал ты на это уведомление или нет. Текст итога (`messages.action_note`) в сервисах, чтобы веб на шаге 5 говорил то же самое |
| Доменные ошибки — реплика через `callback.answer`, а не падение (шаг 4) | `AlreadyInStatus`, `InvalidTransition` и `SnoozeLimitReached` на кнопках — норма, а не баг: двойное нажатие и нажатие на уже закрытом занятии случаются постоянно |
| `/start` не заводит пользователей (шаг 4) | Их создаёт сид (§12.5), а `telegram_id` уникален — заведённый ботом пользователь подрался бы с сид-пользователем. `/start` показывает id, чтобы его было откуда взять для `.env` |
| `allowed_updates` ограничен `message` и `callback_query` (шаг 4) | Остальные типы апдейтов Telegram копит, пока контейнер стоит, и отдаёт пачкой при старте |
| Есть хендлер-заглушка на любой незнакомый `callback_data` (шаг 4) | Без ответа Telegram крутит часики на кнопке около минуты — выглядит как зависший бот |
| Сообщение старше 48 часов не редактируется, действие всё равно записано (шаг 4) | Telegram отдаёт такое как `InaccessibleMessage`. Отказываться из-за этого от перехода статуса было бы хуже: человек нажал осознанно |
| Дев-токен — это `str(user.id)` без подписи и TTL (шаг 5a) | Настоящий Telegram Login Widget требует домен для `/setdomain`, которого на localhost нет (§12.4). Расширять эту схему до продакшен-авторизации не планируется — она размечена как дев-заглушка и в докстринге, и здесь |
| Кнопки веб-экрана (`can_start`/`can_snooze`/`can_complete`/`can_skip`) считает API, а не фронт (шаг 5a) | Инвариант 4: какое действие допустимо — бизнес-правило. Схема `OccurrenceOut` читает уже существующие наборы статусов из `services/occurrences` (`START_FROM`, `can_snooze()` и т.д.) — то же самое, что раньше делал только `ACTIONS` в хендлере бота |
| Доменные ошибки ловит один обработчик `ServiceError` в `app/api/main.py`, не try/except в каждом роутере (шаг 5a) | Аналог `explain()` в хендлерах бота: одно место решает, что `AlreadyInStatus`/`SnoozeLimitReached`/`InvalidTransition` — это 409, а `ValidationError` — 400. Роутеры остаются тонкими и не дублируют эту карту кодов |
| Прокси `/api` в `vite.config.ts` вместо CORS-мидлвари в FastAPI (шаг 5b) | Запрос уходит с dev-сервера Vite, а не из браузера, поэтому для браузера это тот же origin и preflight не нужен вовсе. Бэк остаётся без единой настройки, существующей только ради локальной разработки |
| Свой роутер на `location.hash`, без react-router (шаг 5b) | Пять экранов не окупают зависимость, а хост тут вообще без node — ставить пакет пришлось бы внутри контейнера, с обновлением lock-файла и долгой пересборкой образа. Хэш выбран вместо History API намеренно: dev-сервер Vite отдаёт `index.html` только по корню, и на F5 по адресу привычки понадобился бы фолбэк |
| Кнопки на «Сегодня» рисуются строго по флагам `can_*` из ответа (шаг 5b) | Продолжение решения шага 5a. Фронт не знает ни одного правила §4 — иначе веб и Telegram однажды разойдутся в том, что считают допустимым |
| Отказ действия (409) перечитывает весь список, а не только карточку (шаг 5b) | Отказ почти всегда значит, что статус уже сменился в другом месте: кнопкой в чате или джобом закрытия дня. Показать текст ошибки мало — на экране останутся кнопки, которых уже нет |
| Валидация формы не дублируется на фронте (шаг 5b) | Инвариант 4: непустое название, минимум 5 минут и диапазон дней проверяет `services/habits.py`. В форме только `required`/`min` как подсказка браузера, отказ показывается текстом бэка как есть |
| Расхождение таймзоны браузера и профиля показывается плашкой, а не правит профиль (шаг 5b) | Инвариант 2: источник локального времени один — `User.timezone`. Молча подменить его нельзя: человек мог уехать на неделю и не хотеть сдвигать расписание. Менять — руками в «Настройках» |
| Сетка heatmap строится от календаря, а данные раскладываются по ней (шаг 5b) | Ручка отдаёт только дни, на которые есть occurrence. Если рисовать подряд то, что пришло, дни вне расписания привычки съедут по неделям и картинка соврёт |
| После `UPDATE` привычки роутер вызывает `session.refresh(habit)` перед ответом (шаг 5a) | `Habit.updated_at` — `onupdate=func.now()` на стороне Postgres. При `expire_on_commit=False` после `commit()` это поле не подтягивается само, и синхронный доступ Pydantic к нему на сериализации ловит `MissingGreenlet` (ленивый SELECT вне `await`). Поймано curl'ом на первом же `PATCH /habits/{id}` — без ручного `refresh()` эндпоинты `update_habit`/`archive_habit`/`restore_habit` падали 500 после успешного коммита |

| `change_user_timezone` пересчитывает `paused` вместе с `pending` (находка 4) | Пауза — отложенное будущее, а не история, и переезжать обязана вместе с расписанием. Одна правка в одном месте закрывает и дубли на один день, и 500 при возврате таймзоны. Альтернатива — чинить в `cancel_pause` — оставляла бы 500 достижимым по другим путям |
| `IntegrityError` ловится общим обработчиком и отдаёт 409 (находка 5) | Уникальный индекс `(habit_id, scheduled_at)` — это бизнес-правило «одно занятие на привычку и время», а не сбой инфраструктуры. | Архивация закрывает открытые занятия текущего дня как `skipped` (находка 7) | Архив по §8 — осознанный отказ от привычки, тот же жест, что и «Не получилось». Без этого занятие оставалось живым: пинги продолжали приходить, карточка висела на «Сегодня», а привычки в списке уже не было, и вернуть её из архива человек не мог. | Закрытие дня пропускает записи с `current_due_at` в будущем (находка 6) | Снуз незадолго до полуночи переносит срок в новые сутки, а `local_date` остаётся вчерашним — джоб убивал занятие раньше обещанного кнопкой срока. Занятие остаётся за своим днём в статистике, следующий часовой прогон закроет его, если срок прошёл, а ответа не было. Двигать `local_date` вместе со снузом отвергли: во вчерашнем дне осталась бы дыра, а в новом могло уже быть своё занятие той же привычки |
| Дни паузы в heatmap берутся из `HabitPause`, а не из occurrences (находка 9) | Генератор дни активной паузы пропускает, поэтому `paused` получают только занятия, успевшие появиться до постановки паузы — на горизонте в двое суток. Заставлять генератор писать `paused` отвергли: прошедшие дни длинной паузы это всё равно не закрасило бы |
| Пауза задним числом запрещена (находка 8) | Интервал в прошлом длиннее 14 дней обнулял уже сложившуюся серию (проверено: 11 → 5), при том что дни внутри давно закрыты своими статусами и продолжают считаться. То есть правило §7 применялось только штрафной половиной. §10 выносит ретроспективную отметку за MVP — ограничение действует независимо от того, через какую ручку она пришла |

Дублировать предупреждение в двух местах — верный способ однажды поправить его в одном |
| Список пауз показывает только незакончившиеся (находка 15) | `active_pauses` фильтрует по `cancelled_at IS NULL` и не смотрит на дату окончания, поэтому «снять досрочно» предлагается и для паузы, закончившейся месяц назад. Данные это не портит, но список растёт бесконечно |

## Как отлаживать бота

- **Поставь `SCHEDULER_TICK_SECONDS=5` в `.env`.** По умолчанию 60. После отладки верни обратно, иначе тик в пять секунд будет молотить всё время.
- **Сид ставит «Отжимания» на три минуты вперёд:** `docker compose exec api python -m app.fixtures.seed`, дальше `docker compose logs -f worker bot`.
- **Сид пересоздаёт пользователя.** Каскад по FK уносит вместе с ним все привычки и историю, так что нажатия, сделанные до сида, в БД не останутся.
- **Чтобы уведомления ушли в лог, а не в чат** — очисти `TELEGRAM_BOT_TOKEN`: воркер сам переключится на `LogNotifier`.
- **Смотреть состояние:** `docker compose exec db psql -U postgres -d habits -c "select h.title, o.status, o.snooze_count from occurrences o join habits h on h.id=o.habit_id where o.local_date = current_date;"`

## Находки ручного тестирования

Первые две — про то, что состояние живёт в БД, а чат про это состояние ничего не знает. Дальше — находки сквозной сессии тестирования против §4, §5, §7 и §9.

### 1. Непонятно, что надо подписаться на бота — закрыто дёшево

Telegram не даёт боту написать первым, пока человек не отправил `/start`. Попытка возвращает `TelegramForbiddenError`, а в диспетчере он ловится тем же `except Exception`, что и мигнувшая сеть ([jobs.py:46](backend/app/scheduler/jobs.py)): `notified_at` не проставляется, и следующий тик пробует снова — так до конца дня, пока джоб закрытия не переведёт занятие в `missed`. Человек не получает ничего и нигде об этом не узнаёт: единственный след — логи воркера.

Закрыто фронтом, без миграций: инструкция в «Настройках» и одноразовая подсказка на «Сегодня» с закрытием через `localStorage`. Проверить программно, начал ли человек диалог, нельзя — Telegram про это не сообщает, поэтому подсказка показывается всем и закрывается вручную.

Что осталось несделанным и было бы правильнее: диспетчер должен отличать `TelegramForbiddenError` (повторять бессмысленно, надо сказать человеку) от временного сбоя (надо повторить). Тогда плашка показывалась бы только тем, у кого связь реально не работает. Это требует колонки на `User` и миграции.

### 2. Действие в вебе не отражается в чате — ждёт шага 6

Начал упражнение кнопкой в Telegram, закончил в вебе — сообщение в чате осталось с живыми кнопками и выглядит как «ещё не отвечено».

Причина: бот дописывает итог в `_close_message` ([handlers.py](backend/app/bot/handlers.py)), работая с `callback.message` — сообщение у него в руках, потому что нажатие пришло оттуда же. Когда действие приходит из веба, дотянуться до сообщения не может никто: `message_id` нигде не хранится.

**Сообщений при этом два, а не одно** — первое уведомление и догоняющий пинг, у каждого свой набор живых кнопок. Данные не ломаются: нажатие на протухшую кнопку вернёт `AlreadyInStatus`, бот ответит репликой. Врёт только чат.

Дёшево это не чинится — либо храним `message_id`, либо чат так и остаётся врать.

| `preview_timezone_change` — тот же расчёт, но без записи; за ним ручка `GET /users/timezone-preview` и предупреждение в «Настройках» | `services/habits.py`, `api/routers/users.py`, `screens/SettingsScreen.tsx` |
| `IntegrityError` → 409 отдельным обработчиком, конфликт уходит в лог целиком | `api/main.py` |
| `pause_habit` отбивает `starts_on` раньше сегодняшнего дня по таймзоне владельца; на форме заморозки `min` у поля даты | `services/habits.py`, `screens/HabitScreen.tsx` |
| `stats.heatmap` достраивает дни паузы из `HabitPause`; принимает `habit` и `tz` вместо `habit_id` | `services/stats.py`, `api/routers/habits.py` |

Решения, которые пришлось принять по ходу — спека их не оговаривает:

- **Занятие в heatmap сильнее паузы.** Пауза заполняет только дни, на которых
  записи нет. Иначе день, закрытый как `done` живым занятием (`pause_habit`
  намеренно не трогает `notified`/`snoozed`/`in_progress`), перекрасился бы
  в `paused` — то есть реальное выполнение стёрлось бы из календаря.
- **Дни вне расписания привычки паузой не красятся.** Пауза на 20 дней у
  привычки по пн/ср/пт закрашивает только пн/ср/пт: без паузы этих дней
  в календаре тоже не было бы, и красить их значило бы соврать про расписание.
- **`paused` с прошедшим новым временем удаляется так же, как `pending`.**
  Основание §8 («диспетчер пришлёт уведомление в ту же секунду») для паузы
  срабатывает отложенно — в момент её снятия, но срабатывает.
- **`removed_today` считает только сегодняшний день**, как и просит §8.
  При сдвиге больше суток теоретически может исчезнуть и завтрашнее занятие;
  на горизонте генерации в двое суток это требует переезда почти через
  датную линию поздним вечером. Если такой случай всплывёт — считать по всему
  плану, поле уже отдаётся отдельной ручкой.
- **Таймзону для «сегодня» `pause_habit` берёт из владельца сама**, через
  `session.get(User, habit.user_id)`, а не из аргумента: вызывающих у неё
  трое (роутер, фикстуры, тесты), и «сегодня» у всех должно быть одно.

Проверено на живом стенде: переезд туда-обратно без дублей, предпросмотр
и heatmap паузы совпадают с ожиданием, пауза задним числом — 400.

**Две ловушки в тестах, оставшиеся с прошлой сессии.** Они зелёные, но
привязаны к календарной дате 26.08.2026 и к реальным часам, а не к
переданному `now`:

- `test_предпросмотр_смены_таймзоны_показывает_число_удаляемых_занятий`
  (`test_api_users.py`) — занятие на 19:00 по Москве 26.08 удаляется по Токио
  только после 10:00 UTC. До этого часа и в любой другой день тест покраснеет;
- `test_пауза_без_даты_окончания_ставится_на_неделю` (`test_habits_db.py`) —
  зовёт `pause_habit` без `now` со `starts_on=26.08.2026`. С гардом находки 8
  назавтра это станет паузой задним числом.

Трогать их эта сессия не стала намеренно: правка теста ради зелёного цвета —
именно то, чего просили не делать. Чинятся оба одинаково: передать `now`
и считать даты от него.

### Что сделала сессия «где кончается занятие» (26.08.2026)

Четыре коммита, по одному на находку. `pytest` — 108 тестов, зелёный,
xfail'ов не осталось ни одного.

| Что изменилось | Где |
|---|---|
| `close_local_day` пропускает записи с `current_due_at` в будущем — снуз за полночь доживает до своего срока (находка 6) | `services/occurrences.py` |
| Тот же джоб стал двумя переходами: `pending`/`notified`/`snoozed` → `missed`, `in_progress` → `skipped` (находка 11) | `services/occurrences.py` |
| `archive_habit` гасит открытые занятия сегодняшнего дня как `skipped`; таймзону владельца берёт сама (находка 7) | `services/habits.py`, `services/occurrences.py` |
| `messages.reminder` добавляет «✅ Выполнил» — набор кнопок совпал с вебом (находка 12) | `services/messages.py` |

Решения, которые пришлось принять по ходу:

- **Правило «во что закрывать день» живёт в `DAY_CLOSE_TRANSITIONS`,
  а не в `WHERE`.** После находки 11 массовый UPDATE стал двумя разными
  переходами, и было соблазнительно развести их условием прямо в SQL.
  Инвариант 4 распространяется и на массовые операции: статус occurrence
  решается только в `services/occurrences.py`, поэтому запросов два, а список
  переходов — обычная константа модуля, которую видно глазами.
  `UNRESOLVED_STATUSES` теперь собирается из неё, а не наоборот.
- **`mark_missed` сузился до `MISS_FROM`.** Одиночный аналог джоба не должен
  уметь то, чего джоб больше не делает, иначе `in_progress → missed` вернётся
  через первый же новый вызов. В production-коде у функции вызывающих нет,
  поправлен только `test_transitions.py`.
- **`current_due_at <= at` применяется ко всем четырём статусам, не только
  к `snoozed`.** Спека формулирует оговорку без исключений, а у остальных
  статусов срок в будущем и так не встречается — отдельная ветка была бы
  кодом на случай, которого нет.
- **Архивация сначала удаляет будущие `pending`, потом гасит остаток.**
  В обратном порядке занятие на вечер того же дня получило бы `skipped`
  вместо удаления — то есть в статистику попал бы отказ, которого человек
  не совершал.
- **`paused` архивация не трогает.** Приостановленный день по §7 в расчётах
  не участвует и пингов не порождает; превращать его в отказ незачем.

Проверено на живом стенде в ночь на 27.08.2026 — все четыре критерия
подтверждены (снуз за полночь доживает до срока, брошенный `in_progress`
уходит в `skipped`, кнопки в чате и вебе совпали, архивация гасит пинги).

**Две ловушки живой проверки, обе стоили одного сорванного прогона.**

- **Часы машины автора опережают `Europe/Moscow` на два часа**, а сид живёт
  по Москве. Время в инструкциях, набранное с настенных часов, промахивается:
  привычка, заведённая «на 21:45», получила расписание в прошлом, занятие
  на сегодня не создалось, и уведомления никто не дождался. Все моменты
  в сценариях проверки считать от `now()` в базе
  (`(now() AT TIME ZONE 'Europe/Moscow')::date`, `now() + interval '1 minute'`),
  а не записывать числом.
- **Диспетчер с тиком в 5 секунд успевает влезть между подготовкой данных
  и ручным запуском джоба.** Занятие, которому подвинули `current_due_at`
  в прошлое, он перехватывает и шлёт уведомление. На результат это не влияет,
  но если готовите состояние и проверяете джоб — сцепляйте `psql` и запуск
  в одну команду, а `followup_sent_at` заполняйте сразу.

  Модель — Opus: тут доменные развилки, а не вёрстка.
- **Документация:** README и ERD — механический перенос из кода, хватит Sonnet. C4 и сиквенсы — Opus, потому что вся работа в том, что **не** рисовать.
