# Трекер полезных привычек — требования к MVP

**Версия:** 1.3
**Статус:** согласовано для первой итерации, открытых вопросов нет

---

## 1. Суть продукта

Пользователь заводит привычку, указывает расписание (дни недели + время) и длительность. Приложение напоминает о привычке в назначенное время, позволяет отложить или пропустить выполнение, а после окончания — подтвердить, что привычка выполнена. Накопленная история превращается в стрики и статистику.

**Ключевой принцип:** привычка (шаблон) и её выполнение в конкретный день (occurrence) — это две разные сущности. Вся история, статусы и статистика живут на occurrence.

## 2. Стек и архитектура

| Слой | Технология |
|---|---|
| Бэкенд | Python, FastAPI |
| ORM / миграции | SQLAlchemy (или SQLModel) + Alembic |
| БД | PostgreSQL |
| Планировщик | APScheduler (отдельный процесс-воркер) |
| Telegram-бот | aiogram, режим **polling** (локально) |
| Фронтенд | React + Vite + TypeScript |
| Авторизация | Telegram Login Widget + dev-режим (см. 12.4) |
| Развёртывание | **Docker Compose, локальный запуск** |

### Процессы

| Процесс | Роль |
|---|---|
| `api` | FastAPI: REST для фронта |
| `worker` | APScheduler: три периодические задачи (раздел 6). Держит экземпляр `Bot` **только для отправки** сообщений |
| `bot` | aiogram Dispatcher в режиме polling: принимает нажатия кнопок и пишет результат в БД |
| `web` | React (Vite) |
| `db` | PostgreSQL |

Три бэкенд-процесса делят один кодовый модуль: общие модели, общий сервисный слой. Разделение важно принципиально — если планировщик поднять внутри веб-процесса, то при запуске API в несколько реплик уведомления начнут дублироваться.

Отправка сообщений (`worker`) и приём апдейтов (`bot`) — разные вещи: `Bot.send_message()` работает без polling, поэтому воркеру отдельный слушатель не нужен.

### Слой уведомлений

Отправка спрятана за интерфейсом:

```python
class Notifier(Protocol):
    async def send(self, user: User, text: str, buttons: list[Button]) -> None: ...
```

В MVP одна реализация — `TelegramNotifier`. Web Push добавляется позже как вторая реализация без переписывания бизнес-логики.

Конкретное «сегодня в 19:00 английский».

|---|---|---|

| `scheduled_at` | timestamptz | исходное плановое время |
| `current_due_at` | timestamptz | плановое время с учётом снузов |
| `duration_minutes` | int | снимок `Habit.duration_minutes` на момент создания |
| `status` | enum | см. раздел 4 |
| `snooze_count` | int, default 0 | максимум 5 |
| `notified_at` | timestamptz, nullable | |
| `followup_sent_at` | timestamptz, nullable | догоняющий пинг «Выполнил?» |
| `started_at` | timestamptz, nullable | нажатие «Начал» |
| `finished_at` | timestamptz, nullable | переход в терминальный статус |

Уникальный индекс: `(habit_id, scheduled_at)` — защита от дублей при повторном запуске генератора.

**Поправка к v1.3 (шаг 1).** `duration_minutes` намеренно дублируется на occurrence, хотя длительность есть в Habit. Догоняющий пинг считается как `started_at + duration` (§6.2): если брать длительность из шаблона в момент запроса, то правка привычки среди дня сдвинет таймер уже запущенного выполнения и задним числом изменит прошлые записи. Это противоречит §8 («прошлые и текущие occurrences не трогаются») и принципу, по которому вся история живёт на occurrence.

### HabitPause

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | UUID, PK | |
| `habit_id` | UUID, FK → Habit | |
| `starts_on` | date | |
| `ends_on` | date | **обязательно**, default +7 дней |
| `cancelled_at` | timestamptz, nullable | досрочное снятие паузы |

Дата окончания обязательна намеренно: бессрочная пауза приводит к «мёртвым» привычкам с формально живым стриком.

**Инвариант:** запись `HabitPause` создаётся **только по явному действию пользователя**. Системных пауз в продукте нет — ни архивация, ни отсутствие активности, ни сбой отправки уведомлений не создают паузу автоматически.

## 4. Жизненный цикл occurrence

```
                    ┌─────────┐
                    │ pending │◄──── создан ночным генератором
                    └────┬────┘
                         │ планировщик: current_due_at <= now
                         ▼
    ┌──────────────►┌──────────┐
    │               │ notified │
    │               └────┬─────┘
    │  «+5 мин»          │
    │  (snooze_count<5)  ├──── «Начал» ───────►┌─────────────┐
    │                    │                     │ in_progress │
    ▼                    │                     └──────┬──────┘
┌─────────┐              │                            │ «Выполнил»
│ snoozed │              │                            ▼
└─────────┘              │                        ┌──────┐
                         ├──── «Пропустить» ─►    │ done │
                         │                        └──────┘
                         ▼
                    ┌─────────┐          ┌────────┐
                    │ skipped │          │ missed │◄── ночной джоб
                    └─────────┘          └────────┘

    pending ──► paused ──► pending   (постановка / снятие паузы)
```

**Терминальные статусы:** `done`, `skipped`, `missed`, `paused`.

| Переход | Триггер |
|---|---|
| `pending → notified` | планировщик, `current_due_at <= now` |
| `notified → snoozed` | кнопка «+5 мин», если `snooze_count < 5`; `current_due_at += 5 мин`, `snooze_count++` |
| `snoozed → notified` | планировщик, по наступлении нового `current_due_at` |
| `notified/snoozed → in_progress` | кнопка «Начал», пишем `started_at` |
| `notified/snoozed → skipped` | кнопка «Пропустить сегодня» |
| `in_progress → done` | кнопка «Выполнил» |
| `* → missed` | ночной джоб для всего нетерминального |
| `pending → paused` | постановка привычки на паузу |
| `paused → pending` | снятие паузы, если время ещё не прошло |

При `snooze_count = 5` кнопка «+5 мин» больше не показывается — остаются только «Начал» и «Пропустить».

## 5. Логика уведомлений

### Первое уведомление (в момент `current_due_at`)

> ⏰ **Английский** — 19:00, 30 мин
> `▶️ Начал` `⏰ +5 мин` `🚫 Пропустить сегодня`

### Догоняющий пинг

Отправляется один раз, `followup_sent_at` защищает от повторов.

| Ситуация | Когда шлём | Кнопки |
|---|---|---|
| Пользователь нажал «Начал» | `started_at + duration_minutes` | `✅ Выполнил` `❌ Не получилось` |
| Пользователь не отреагировал | `current_due_at + duration_minutes` | `✅ Выполнил` `❌ Пропустить` |

Вторая строка нужна, чтобы не потерять человека, который проигнорировал уведомление, но реально пошёл и сделал зарядку. Снуз сдвигает `current_due_at`, поэтому таймер догоняющего пинга сдвигается вместе с ним автоматически.

Если пользователь не отреагировал и на догоняющий пинг — ночной джоб проставит `missed`.

## 6. Планировщик

Все три задачи опрашивают БД. Отложенные таймеры в памяти не используются: они не переживают рестарт и деплой.

### 6.1 Генератор occurrences — раз в сутки, 03:00 UTC

Для каждой активной привычки создаёт occurrences на ближайшие 2 суток вперёд (запас на случай пропуска запуска). Идемпотентен за счёт уникального индекса. Пропускает дни, попадающие в активную паузу.

### 6.2 Диспетчер уведомлений — каждую минуту

```sql
-- к отправке первого уведомления
SELECT * FROM occurrences
WHERE status IN ('pending', 'snoozed') AND current_due_at <= now();

-- к отправке догоняющего пинга
SELECT * FROM occurrences
WHERE followup_sent_at IS NULL AND (
  (status = 'in_progress' AND started_at + duration <= now())
  OR (status = 'notified' AND current_due_at + duration <= now())
);
```

### 6.3 Закрытие дня — ежечасно

Для каждого пользователя, у которого по его таймзоне наступила полночь: все нетерминальные occurrences за прошедшую дату → `missed`. Запуск ежечасно, потому что полночь наступает в разное время в разных таймзонах.

## 7. Стрики и статистика

### Правила стрика (по каждой привычке отдельно)

- `done` → серия +1
- `skipped` и `missed` → серия обнуляется (одинаково, по решению заказчика)
- дни паузы **не участвуют в расчёте**: не увеличивают и не ломают серию
- **если пауза длилась дольше 14 дней подряд — текущая серия обнуляется при возобновлении.** Рекорд (`best_streak`) сохраняется всегда

Верхнего ограничения на длину паузы нет: правило 14 дней работает вместо запрета. Но пользователь должен узнать о последствиях **до** того, как нажмёт кнопку, а не после. Если выбранный интервал больше 14 дней, форма заморозки показывает предупреждение:

> ⚠️ Пауза дольше 14 дней обнулит текущую серию (сейчас 23 дня). Рекорд сохранится.

Пример: 10 дней подряд → пауза 5 дней → выполнено → серия 11. Та же ситуация с паузой в 20 дней → серия 1, рекорд остаётся 10.

### Метрики MVP

- текущая серия и рекорд по привычке
- процент выполнения за 30 дней: `done / (done + skipped + missed)`
- календарь-heatmap («травка») по дням, с визуально отличным цветом для `paused`

Все метрики считаются запросами к `occurrences`, отдельных таблиц не требуется. Денормализацию делать только если появятся проблемы с производительностью.

## 8. Изменение привычки

Правка происходит **на месте**, без версионирования:

1. Обновляем поля `Habit`.
2. Удаляем будущие occurrences в статусе `pending`.
3. Генератор создаёт новые по обновлённому расписанию.

Прошлые и текущие occurrences не трогаются — история остаётся достоверной.

**Архивация** (`is_archived = true`) — вместо удаления. Будущие `pending` удаляются, история сохраняется.

Архивация — не пауза, и `HabitPause` при ней не создаётся. Но за время архива occurrences не генерируются, а значит в расчёте серии эти дни просто отсутствуют — то есть архив работал бы как бесконечная пауза в обход правила 14 дней. Поэтому: **при восстановлении привычки из архива текущая серия начинается с нуля, рекорд сохраняется.** Архивация трактуется как отказ от привычки, а не как перерыв в ней.

### Смена таймзоны пользователем

При изменении `User.timezone` пересчитываются **все occurrences в статусе `pending`** по всем его привычкам: `scheduled_at` и `current_due_at` собираются заново из `schedule_time` в новой таймзоне.

Occurrences в статусах `notified`, `snoozed` и `in_progress` не трогаются — процесс уже запущен, сдвигать его на лету означало бы отправить уведомление второй раз или потерять таймер. Прошлые и терминальные записи неизменны: `local_date` фиксирует день, в который событие реально произошло.

## 9. Экраны фронтенда

| Экран | Содержимое |
|---|---|
| Вход | Telegram Login Widget, выбор таймзоны (по умолчанию — из браузера) |
| Сегодня | список occurrences на сегодня с их статусами, кнопки действий дублируют кнопки из TG |
| Мои привычки | список, создание, редактирование, пауза, архивация |
| Привычка | детали, серия, рекорд, heatmap, процент за 30 дней |
| Настройки | таймзона, канал уведомлений (задел на будущее) |

Действия доступны и в вебе, и в Telegram — состояние одно и то же, живёт в БД.

### Валидация формы привычки

При создании и редактировании проверяется пересечение окон с другими активными привычками. Окно привычки — `schedule_time … schedule_time + duration_minutes`.

Пересечение **подсвечивается, но не блокирует сохранение**:

> ⚠️ Пересекается с «Тренировка» (19:30–20:00)

Снузы в проверке **не учитываются**: они происходят в рантайме и предсказать их на этапе создания нельзя. Формально это значит, что отложенная привычка может наложиться на следующую — это допустимо, пользователь сам управляет своим временем.

## 10. Не входит в MVP

- Web Push и PWA (нужен только интерфейс `Notifier` под будущую реализацию)
- Ачивки, уровни, очки, виртуальный питомец
- Несколько напоминаний в день для одной привычки
- Привычки без привязки к дням недели («3 раза в неделю»)
- Количественные привычки («8 стаканов воды»)
- **Ретроспективная отметка** прошедших дней. Статус `missed` окончателен: если пользователь не отреагировал ни на первое уведомление, ни на догоняющий пинг, день закрывается как пропущенный и изменить его нельзя
- Заметки к выполнению, трекинг настроения
- Социальные функции, шаринг, экспорт

## 11. Осознанно принятые ограничения

Решения, которые упрощают MVP ценой некоторой строгости. Зафиксированы здесь, чтобы через месяц не выглядеть багами.

| Ограничение | Последствие | Почему так |
|---|---|---|
| Пересечения подсвечиваются, но не блокируются | Можно создать две привычки на одно время | Пользователь взрослый, запрет раздражает сильнее, чем помогает |
| Снузы не участвуют в проверке пересечений | Отложенная привычка может наложиться на следующую | Непредсказуемо на этапе создания |
| Нет верхнего лимита длины паузы | Пауза на полгода возможна | Правило 14 дней + предупреждение решают задачу мягче запрета |
| `missed` неизменяем | Забытое уведомление навсегда портит статистику | Ретроспективная правка обесценивает метрику; вынесено за MVP |
| Одно время на привычку | «Витамины утром и вечером» = две привычки | Упрощает и модель, и планировщик |

## 12. Локальное развёртывание

Цель — `docker compose up` и работающее приложение на своей машине. Никакого облачного хостинга в MVP.

### 12.1 Структура репозитория

```
habit-tracker/
├── docker-compose.yml
├── .env.example
├── backend/
│   ├── Dockerfile
│   ├── pyproject.toml
│   ├── alembic/
│   └── app/
│       ├── models/        # SQLAlchemy — общие для всех процессов
│       ├── services/      # бизнес-логика: переходы статусов, стрики
│       ├── api/           # FastAPI-роутеры
│       ├── bot/           # aiogram: хендлеры кнопок
│       ├── scheduler/     # APScheduler: три джоба
│       ├── notifier.py    # Protocol + TelegramNotifier
│       └── config.py      # pydantic-settings, чтение .env
└── frontend/
    ├── Dockerfile
    └── src/
```

Один образ бэкенда на три сервиса — меняется только команда запуска:

| Сервис | Команда |
|---|---|
| `api` | `uvicorn app.api.main:app --host 0.0.0.0 --reload` |
| `worker` | `python -m app.scheduler.main` |
| `bot` | `python -m app.bot.main` |

### 12.2 Сервисы compose

| Сервис | Образ / сборка | Порт |
|---|---|---|
| `db` | `postgres:16-alpine` | 5432 |
| `migrate` | сборка `backend/`, one-shot `alembic upgrade head` | — |
| `api` | сборка `backend/` | 8000 |
| `worker` | сборка `backend/` | — |
| `bot` | сборка `backend/` | — |
| `web` | сборка `frontend/` | 5173 |

Обязательные детали, без которых первый запуск не взлетит:

- **Healthcheck у `db`** (`pg_isready`) и `depends_on: condition: service_healthy` у остальных. Без этого `api` стартует раньше, чем Postgres примет соединения, и упадёт с невнятной ошибкой — классическая ловушка первого проекта.
- **Volume для данных Postgres**, иначе БД будет обнуляться при каждом `docker compose down`.
- **`migrate` как отдельный one-shot сервис**, от которого зависят `api`, `worker` и `bot`. Если гонять миграции в entrypoint каждого — три процесса подерутся за блокировку Alembic.
- **`TZ=UTC` во всех контейнерах.** Вся работа с таймзонами — в коде, через `User.timezone`. Контейнер, унаследовавший локальную таймзону хоста, ломает расчёт `local_date` и джоб закрытия дня.
- **Монтирование исходников как volume** (`./backend:/app`) + `--reload` — иначе каждое изменение кода потребует пересборки образа.
- **`CHOKIDAR_USEPOLLING=true` для `web`** — на Docker Desktop и WSL2 hot reload Vite без этого не видит изменения файлов.

### 12.3 Переменные окружения

```
POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB
DATABASE_URL=postgresql+asyncpg://user:pass@db:5432/habits
TELEGRAM_BOT_TOKEN=
DEV_AUTH=true
SCHEDULER_TICK_SECONDS=60
```

Хост БД — `db` (имя сервиса в compose), не `localhost`.

`SCHEDULER_TICK_SECONDS` вынесен в конфиг намеренно: на отладке ставится 5 секунд, чтобы прогнать весь жизненный цикл occurrence за пару минут вместо часа.

### 12.4 Авторизация локально

**Проблема:** Telegram Login Widget требует реальный домен, привязанный к боту через `/setdomain` у BotFather. `localhost` он не принимает — виджет просто не отрисуется.

**Решение для локальной разработки:** флаг `DEV_AUTH=true` включает эндпоинт `POST /auth/dev-login`, который выдаёт сессию для сида пользователя из фикстур, минуя Telegram. Фронт при `DEV_AUTH` показывает кнопку «Войти как тестовый пользователь» вместо виджета.

Для проверки настоящего входа — временный туннель (`cloudflared tunnel --url http://localhost:8000`) и его домен в `/setdomain`.

**Важно:** уведомления работают локально без всяких туннелей. Polling сам ходит к Telegram наружу, входящий трафик не нужен — достаточно указать `TELEGRAM_BOT_TOKEN` и один раз написать боту `/start`, чтобы он узнал твой `chat_id`.

### 12.5 Фикстуры для отладки

Отдельная команда `python -m app.fixtures.seed` создаёт тестового пользователя и набор привычек: одну на 5 минут, одну на 30, одну на паузе, одну с историей на 60 дней назад с разными статусами. Без этого heatmap и стрики нечем проверять — ждать неделю ради одного графика бессмысленно.
